# Inline and portable delivery

## Inline

Use the host's visualization surface and current theme variables. In T3 Code, pass the generated HTML to `html_preview`, inspect it, then call `html_render`. Avoid starting a server for a self-contained snapshot. Other hosts may require an HTML fragment or another artifact format; follow that surface's contract rather than pasting unsupported markup into chat.

The renderer's `--mode inline` output has a transparent outer surface and host theme variables. It contains no fixed palette or remote resources. If the host needs a fragment, extract the report's styles, main element and script rather than introducing a second rendering implementation.

## Standalone / Claude attachment

Use `--mode standalone --tokens ~/design-language/tokens.css` to inline the installed design-language tokens, which are generated from `@filipgutica/ui`. This keeps the export readable without host CSS, a Vue runtime, an npm install, or network access. The same normalized snapshot and view function drive both modes.

The HTML file is an uploadable, self-contained snapshot: embed its dataset, styles and JavaScript; keep filters local. It must work without `window.openai`, a connector, a server or a fetch request. Open the actual standalone file without host-provided styles before calling it portable. Describe it as ready to attach to Claude, not as uploaded or proven compatible with a particular Claude deployment unless that was verified.

For an existing application, use its components and tokens; the Vue package owns those components. Project-specific skills own source queries, normalization and provider verification; this shared layer owns presentation and export. A new provider integration does not by itself justify a new design system or a provider-specific Vue component.

## Claude UX review

When requested or required by host rules, use the host's supported Claude delegation route. Prefer the configured design/UX model; honor an explicitly named model. Give a read-only judge:

- The audience, task and actual design-system owner.
- The exact generated file, its source contract, and requested viewport sizes.
- The controls and counts that must remain; the chosen density tradeoff.
- A way to preview the complete file without copying it into the prompt. An exact script-free initial DOM is acceptable for static visual inspection if it is generated by the same view function; it cannot prove picker behavior.
- A completion request for actionable findings with selectors, impact and smallest fixes, plus inspected widths/themes and interaction limits.

Require the judge to inspect the actual artifact. Do not accept a reconstructed subset as equivalent, or describe code inspection as clicking controls. Main-thread acceptance checks the final artifact, not just the review verdict. Two rounds are useful when requested; avoid an automatic unbounded council loop.

## Mechanical checks

Use the renderer's validation before display. Then exercise every available region/window pair in the actual DOM: counts, totals, category coverage, percentage denominators, selected UTC bounds and empty states. Compare pre-script content and ARIA labels with the initial interactive state. Check percentage rounding near zero and 100%.

At desktop width, confirm the overview and detail are readable together. Do not distort proportional bars to give tiny errors a minimum width; preserve labeled error counts alongside the chart. On narrow screens, keep every important category visible; the count renderer uses responsive rows rather than a clipped wide table. For other wide tables that need horizontal scrolling, preserve row-label context. Check light/dark contrast and scrolling on the real output. Keep this verification bounded to the artifact; no live telemetry re-query is needed for every visual refinement.
