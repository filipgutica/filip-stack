# Flaky tests and agents

## Recognize the failure and measure it

A flaky test fails sometimes without any code change. When an agent sees a red test, it tries to fix the code, even when the test is flaky. For engineers working with agents, this makes flakiness a problem to measure before directing a repair.

Start by rerunning each test 20 times on the same commit and counting its failures. Use the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

Keep the commit the same throughout the measurement. The question is specific: how many times does each test fail across those 20 runs? Record the failure count for each test, so the measurement describes that test’s results across the full set of runs.

Agents tend to rerun until green or weaken the assertion. When reviewing an agent’s response to a failure, look for those actions. A green result after repeated attempts is one result within the sequence; the failure count preserves the rest. A weakened assertion changes what the test requires. Keep those actions distinct from measuring how often the test fails without a code change.

## Quarantine a known-flaky test while it is fixed

A required gate is a check that must pass. When it sometimes fails, it teaches agents and people to ignore it. A flaky test in that gate therefore affects how both respond to its failures.

Quarantine means moving a known-flaky test out of the required gate while it is fixed, with an owner and a date. Apply it to a test already known to be flaky. Keep the work explicit:

1. Move the known-flaky test out of the required gate.
2. Assign an owner.
3. Set a date.
4. Fix the test while it is quarantined.

The owner and date are part of quarantine. Include both when describing the work, alongside the test that needs fixing. This gives the engineer and agent a concrete task to follow instead of another attempt to rerun until green.

# Flaky tests and agents

## 1. What a red test teaches

An agent that sees a red test tries to fix the code. It does this even when the test is flaky: a test that sometimes fails without any code change. That distinction matters when you ask an agent to work through failing tests. The agent tries to fix the code, but a flaky test can fail while the code stays the same.

Agents tend to respond in two ways: rerun until green, or weaken the assertion. Neither response tells you how often the test fails on unchanged code. A green rerun is one result; measuring flakiness requires counting failures across repeated runs.

For engineers, the problem also concerns the required gate. A required gate that sometimes fails teaches agents and people to ignore it. Keeping a known-flaky test in that gate leaves both responding to a check that sometimes fails without a code change.

Keep these questions separate: “Did this run fail?” and “Does this test sometimes fail on the same commit?” The first identifies a red result. The second is the question the flakiness measurement addresses.

## 2. Measure failures, then quarantine with ownership

To measure flakiness, rerun each test **20 times on the same commit** and count its failures. Keep the commit the same throughout those runs: the measurement is repeated test results without a code change.

Use the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

Read the failure count across all 20 runs, rather than rerunning only until a green result appears. The question is how many runs failed on that commit, not whether one of the reruns passed.

For a known-flaky test, quarantine means moving it out of the required gate while it is fixed, **with an owner and a date**. Those details belong together: the test leaves the required gate, the fix has an owner, and the quarantine has a date.

This lesson uses the author’s own rubric, not a vendor’s. Its focus is measuring failures on unchanged code and quarantining known-flaky tests with ownership and a date. Use those terms precisely when discussing a red test with an agent.
