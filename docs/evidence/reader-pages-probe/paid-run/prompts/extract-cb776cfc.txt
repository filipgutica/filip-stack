# Flaky tests and agents

## 1. Measure failures on the same commit

A flaky test sometimes fails without any code change. When an agent sees a red test, it tries to fix the code, even when the test is flaky. Engineers need to measure that flakiness before asking an agent to act on the failure.

Start with the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

The measurement is specific: rerun each test 20 times on the same commit, and count its failures. Keep the commit unchanged throughout those runs. For each test, the result you need is the number of failures across all 20 attempts.

Use this sequence:

1. Select the commit to measure.
2. Run each test 20 times on that commit.
3. Count the failures for each test.

An agent tends to rerun a failing test until it turns green, or to weaken the assertion. The audit gives those reruns a different stopping point: complete the 20 runs, including failures in the count. A green result partway through the sequence does not end the measurement.

## 2. Keep the required gate meaningful

A required gate is a set of tests that must pass. When that gate sometimes fails, it teaches agents and people to ignore it. A known-flaky test therefore needs an explicit place while someone fixes it.

Quarantine means moving that test out of the required gate while it is fixed, with an owner and a date. Those details belong together: the test leaves the required gate, someone owns the work, and the quarantine has a date.

For a known-flaky test, record:

- The test being quarantined.
- The owner responsible for fixing it.
- The date attached to the quarantine.

Keep the response to flakiness explicit when directing an agent. Use the measured failure count, identify the known-flaky test, and specify its quarantine with an owner and a date. Rerunning until green or weakening the assertion does not provide those quarantine details.
