# Flaky tests and agents

## 1. Understand what a red test asks the agent to do

Check for flakiness before treating a red test as a request to change the code. A flaky test fails sometimes without any code change. Its failure alone does not establish that the code needs a fix.

An agent that sees a red test tries to fix the code, even when the test is flaky. The agent’s response can therefore start from a false premise: the test failed, so the code must change.

Agents tend to rerun tests until they turn green, or to weaken the assertion. Neither response answers the question you need to ask: does this test sometimes fail on unchanged code? A green rerun is consistent with flakiness. A weaker assertion changes what the test checks.

The required gate matters here. A gate that sometimes fails teaches agents and people to ignore it. Keep that consequence in view when deciding how to handle a known-flaky test.

## 2. Measure flakiness and give quarantine an owner

Measure flakiness by rerunning each test 20 times on the same commit and counting failures. Keep the commit unchanged throughout those runs. The measurement is the failure count across all 20 runs, so continue counting even if a failed run is followed by a passing run.

Use the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

Read the results against the question from the first section: which tests fail sometimes without a code change? Do not treat a later passing run as an answer to an earlier failure. Both results belong in the count.

For a known-flaky test, quarantine means moving it out of the required gate while it is fixed. Quarantine includes an owner and a date. Those details belong with the decision to remove the test from the gate.

Use three questions to guide this lesson’s review:

- Was each test rerun 20 times on the same commit, with failures counted?
- Was each quarantined test already known to be flaky?
- Does each quarantine have an owner and a date while the test is fixed?

# Flaky tests and agents

## 1. Recognize the failure before changing code

A flaky test sometimes fails without any code change. When an agent sees a red test, it tries to fix the code, even when the test is flaky. Engineers need to account for that behavior when they ask agents to work with tests.

Start by measuring failures on unchanged code. Run the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

The measurement is specific: rerun each test 20 times on the same commit and count its failures. Keep the commit fixed throughout the runs. Changing code between attempts would no longer follow this measurement procedure.

Agents tend to rerun tests until they turn green or weaken an assertion. Neither action measures how often the original test fails across the specified runs. A green rerun is one result; the audit calls for a failure count across all 20 attempts. Keep that distinction clear when reviewing an agent’s response to a red test.

## 2. Measure failures and quarantine known flakes

Use the audit results to examine each test separately. For each test, count how many of its 20 runs failed. Do not stop counting when a later attempt passes. The procedure asks for the complete set of runs on the same commit.

Keep the measurement distinct from the response to a known-flaky test. Counting failures measures flakiness. Quarantine means moving a known-flaky test out of the required gate while it is fixed. A required gate is a check that must pass.

When you quarantine a test, give it an owner and a date. Those details belong with the decision to move it out of the gate. Quarantine includes the work to fix the test; removing it from the required checks is only part of that arrangement.

A required gate that sometimes fails teaches agents and people to ignore it. That consequence matters when deciding how to handle a known flake: leaving it required continues to expose both to intermittent failures.
