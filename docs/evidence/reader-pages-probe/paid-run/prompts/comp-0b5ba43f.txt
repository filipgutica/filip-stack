# Flaky tests and agents

## 1. A red test can send an agent toward the wrong fix

When a test is known to be flaky, quarantine it while it is fixed. Give it an owner and a date.

A flaky test fails sometimes without any code change. An agent that sees a red test tries to fix the code, even when the test is flaky. That creates a problem for engineers: the agent responds to the failure, but the failure can occur with unchanged code.

Agents tend to rerun tests until they turn green, or to weaken the assertion. Keep those tendencies in mind when you review an agent’s response to a failing test. Look at whether it changed the code, repeated the run, or weakened what the test checks.

The required gate also matters. A gate that sometimes fails teaches agents and people to ignore it. Leaving a known-flaky test in that gate keeps exposing both to failures that occur without code changes.

This lesson uses the author’s own rubric. It does not come from a vendor. The rubric focuses on measuring failures and handling known-flaky tests while they are fixed.

## 2. Measure failures, then quarantine known-flaky tests

Measure flakiness by running each test 20 times on the same commit and counting its failures. Keep the commit the same throughout those runs.

Use the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

For this lesson’s measurement, the count of failures across 20 runs is the result to record. A run that turns green is still part of that set. Count the failures across the full set rather than stopping when a rerun passes.

Once a test is known to be flaky, quarantine it. Quarantine means moving the test out of the required gate while it is fixed. It must have an owner and a date.

Use these points when reviewing the work:

- **Measurement:** Each test ran 20 times on the same commit, and failures were counted.
- **Quarantine:** The known-flaky test is outside the required gate while it is fixed.
- **Responsibility:** The quarantined test has an owner and a date.
