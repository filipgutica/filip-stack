# Flaky tests and agents

## 1. What a red test teaches

An agent that sees a red test tries to fix the code. That response becomes a problem when the test is flaky: a flaky test sometimes fails without any code change. The agent is responding to a failure, but the failure does not necessarily mean the code needs a fix.

Keep those two statements separate when judging an agent’s response. “The test failed” describes the result. “The code needs changing” is a conclusion that a flaky test does not establish on its own.

Agents tend to respond to this uncertainty by rerunning until green or weakening the assertion. Neither response addresses the known flakiness. Rerunning until green accepts a passing result after failures; weakening the assertion changes what the test requires.

The lesson reaches beyond one agent or one test. A required gate that sometimes fails teaches agents and people to ignore it. The engineering task is therefore to address the flaky test, including its place in the required gate, rather than treating an eventual green result as the end of the work.

## 2. Measure the failures, then assign the fix

Measure flakiness by rerunning each test 20 times on the same commit and counting failures. Keep the commit the same: the question is how often the test fails without a code change.

Use the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

The purpose of these reruns is to count failures across the 20 runs. This differs from rerunning until green: a green result is part of the measurement, rather than a reason to stop counting.

For a known-flaky test, quarantine means moving it out of the required gate while it is fixed. Quarantine includes an owner and a date. Moving the test is only part of that definition; the owner and date belong with it.

Use those facts to assess the response: were failures counted over 20 runs on the same commit? If the test was quarantined, was it moved out of the required gate while being fixed, with an owner and a date?
