# Flaky tests and agents

## 1. Understand what a red test teaches

A flaky test sometimes fails without any code change. An agent that sees a red test tries to fix the code, even when the test is flaky. That creates a problem for engineers: the agent responds to a failure that can occur while the code stays the same.

Agents tend to rerun tests until they turn green, or to weaken the assertion. Neither response measures how often the unchanged test fails. A green rerun records a pass; it does not erase the failures from earlier runs.

This matters when the test belongs to a required gate. A required gate that sometimes fails teaches agents and people to ignore it. The same gate that requires a passing result also produces failures without a code change.

Keep these two points together when you assess a red test: agents try to fix code after a failure, and flaky tests can fail without code changes. The lesson begins with that mismatch.

## 2. Measure failures and quarantine known flakiness

To measure flakiness, rerun each test 20 times on the same commit and count its failures. Keep the commit the same throughout the measurement. Count failures across all 20 runs, including failures followed by passing runs.

Use the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

The measurement asks how often each test fails across those runs. Rerunning until green asks only whether another run passes. Keep the full failure count when you assess the test, rather than stopping the assessment at its first green result.

For a known-flaky test, quarantine means moving it out of the required gate while it is fixed. Quarantine includes an owner and a date. Removing the test from the gate is only part of that definition; the owner, date, and work to fix it belong with the quarantine.

Use these questions as this lesson’s rubric:

- Was each test run 20 times on the same commit?
- Were failures counted?
- Does each quarantine include an owner and a date while the test is fixed?
