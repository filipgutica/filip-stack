# Flaky tests and agents

## Recognize the failure before changing code

A flaky test sometimes fails without any code change. When an agent sees a red test, it tries to fix the code, even when the test is flaky. For an engineer working with agents, that makes flakiness part of deciding how to respond to a failure.

Start by measuring how often each test fails on the same commit. Run the audit script:

```sh
scripts/flake-scan.mjs --runs 20 --json
```

The measurement is specific: run each test 20 times and count its failures. Keep the commit the same throughout those runs. This gives you a failure count for each test under the condition that matters here: the code has not changed.

Agents tend to rerun tests until they turn green, or to weaken the assertion. Neither response answers the measurement question. A green rerun gives you a passing result; the audit asks how many failures occurred across all 20 runs. Keep that distinction clear when reviewing an agent’s response to a red test.

## Quarantine known flakiness while fixing it

A required gate is a check that must pass. When that gate sometimes fails, it teaches agents and people to ignore it. The consequence extends beyond the individual failure: the required check becomes something they learn to disregard.

For a known-flaky test, quarantine means moving it out of the required gate while it is fixed, with an owner and a date. Treat those as parts of the same action. The test leaves the required gate temporarily, and its repair has both a named owner and a date attached.

When arranging quarantine, make each part explicit:

1. Identify the known-flaky test.
2. Move it out of the required gate while it is fixed.
3. Assign an owner.
4. Set a date.

Use the failure count when discussing the test’s flakiness. Use the owner and date when discussing its repair. These answer different engineering questions: how often the test failed during measurement, who owns the fix, and what date is attached to that work.
